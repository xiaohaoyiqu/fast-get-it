欲求达下载工具：QQ Bot 接入注意事项
整理日期：2026-10-31

一、当前是否适合接入

可以作为 QQ Bot 的下载后台。现有平台适配器、任务管理、取消、重试和下载记录都能复用，但还需要补充机器人任务服务，处理用户权限、排队限额、消息去重和文件回传。

目前更适合先做自己或熟人小群使用的版本。公开多人使用前，需要进一步验证并发、账号隔离、资源额度和长期运行稳定性。

本文中的队列容量和并发数量属于建议起始配置，不代表项目已经实现或完成这些配置的验收。

二、推荐调用流程

QQ 消息 → 身份与链接检查 → 有容量上限的队列 → 下载任务 → 结果回传

收到“/下载 链接”后，尽快返回任务编号，不要让消息处理函数一直等待下载结束。后台执行下载，再提供以下命令：

1. /下载 链接
2. /进度 任务编号
3. /取消 任务编号
4. /重试 任务编号

进度消息需要合并和限频，避免每下载一个文件就发送一条消息。

建议由一个常驻后台统一管理下载任务和账号会话，复用现有 TaskManager。避免每条消息都启动一整套下载进程、浏览器和账号会话。

三、当前 CLI 需要注意的地方

代码位置：run_software.py 中的 download_target()。

当前实现等待任务结束后直接返回 0，没有根据下载最终状态设置退出码。因此，Bot 只看进程返回 0，可能把失败任务误判为成功。现有控制台输出主要面向人工阅读，也不宜作为稳定的机器接口。

正式接入应读取真实任务状态，返回结构化结果，至少包括：

1. 任务编号。
2. 当前状态及最终状态。
3. 成功文件列表和失败数量。
4. 经过脱敏的失败原因。
5. 是否可以重试。

如果暂时通过子进程调用 CLI，应使用独立参数列表传参，不要把 QQ 消息拼成 shell 命令；同时补齐可靠的结果读取方式。

四、用户权限与任务归属

每个任务至少记录发起人、来源群或私聊、原消息标识，以及允许回传结果的位置。

查询、取消、重试和领取文件时，都要验证任务归属。普通用户只能操作自己有权限的任务，管理员权限应单独配置。

现有 owner_id 用于运行实例管理，不能当作 QQ 用户权限控制。任务编号本身也不是访问凭证。

需要防止以下情况：

1. 猜到任务编号后读取他人的下载结果。
2. 取消或重试他人的任务。
3. 把私聊任务的结果发送到群里。
4. 通过共享登录账号，向所有群成员暴露私密作品或个人收藏。

Cookie、代理修改、插件安装、清空记录等功能只应由管理员操作，不应直接开放为普通群命令。

五、队列、并发和资源限制

现有下载并发控制不能替代入口排队限制。大量待处理请求仍可能占用线程、磁盘和浏览器资源。

私人小群试用可采用以下起始配置，再根据机器表现调整：

1. 每人最多 1 个运行任务、2 个排队任务。
2. 全局并发先从 2 个开始，浏览器任务更保守。
3. 队列容量先设为 20 个，满后明确提示稍后重试。
4. 默认只允许单作品下载。
5. 作者、收藏等批量下载仅管理员使用。
6. 设置单任务文件数量、总字节数、总时长和最低剩余磁盘空间。

还应按来源平台限制请求速率。多个群共用一个登录账号时，不能只按单个 QQ 用户计算访问频率。

遇到平台限流或长时间冷却，应向用户说明当前状态，避免连续重试。

六、下载完成与发送成功分别记录

文件下载成功后，上传 QQ 仍可能失败。建议分别记录：已下载、待发送、已发送、发送失败。

发送失败时只重试回传，避免重新下载。保存原消息与任务、发送结果之间的关联，避免重复回传。

官方 QQ Bot：
按群聊、单聊等实际接口核对媒体上传、消息发送和回调要求。本机下载路径不是接收方可以直接访问的地址。

OneBot：
规范支持通过本地路径、URL、Base64 等形式发送部分媒体，但实际能力还取决于协议实现。本地路径必须能被运行协议端的进程访问，分机器或容器部署时需要明确共享目录或传输方式。

不要预设所有接入方式都支持相同的群文件、视频格式或文件大小。接入时以具体接口和实现的当前文档、实测结果为准。

大量图片可以限制预览数量，再按实际支持的能力提供文件包或带权限、有效期的下载链接。结果文件应设置保留期限，发送完成或过期后按规则清理。

七、链接和作品信息的安全处理

Bot 只接收允许的平台链接和少量明确参数，下载目录由后台生成。不要允许用户指定任意本地路径、代理、请求头或插件代码。

保留现有 URL 安全检查，并覆盖跳转后的地址，阻止访问本机、内网和云元数据地址。若允许普通网页下载，应重点验证域名解析和重定向处理，不要仅检查用户最初输入的 URL。

作品标题、描述和错误信息均属于不可信输入。使用 OneBot 时，优先构造文本消息段，不要把作品信息直接拼接成 CQ 码。

群内错误回复需要脱敏，不应包含 Cookie、令牌、代理认证信息、本机路径或原始请求头。

机器人管理接口应使用鉴权，并限制可访问范围；如果使用公网回调，按所选接入方式验证请求来源。

八、平台实测范围与无人值守限制

截至本文整理时，Twitter、Bluesky、Pixiv 公开作品、E-Hentai 和普通网页已有少量图片样本的实站验证，可以考虑作为首批接入范围。

这些样本不代表所有功能均已通过长期、批量或视频下载验收。Pixiv 的公开作品验证也不能替代登录后的收藏等功能验收。

目前仍需注意：

1. Google 反向搜图遇到人机验证。
2. JM 遇到 Cloudflare 403，尚未完成章节下载验收。
3. Instagram 帖子和 Reels 尚未充分验收。
4. ExHentai 未完成独立登录会话的实站验证。

上述情况应返回“需要管理员处理登录或验证”等明确状态，并暂停对应平台的连续重试。

群聊回传应设置内容范围。成人内容来源不宜默认开放，尤其不能把共用账号可访问的内容自动视为所有群成员均可领取。

九、数据隔离、重启与长期运行

建议为 Bot 单独配置数据目录、Cookie、下载目录和文件保留期限，避免与桌面端混用个人记录。项目可通过 YUQIUDA_HOME 和 YUQIUDA_OUTPUT_DIR 配置相关目录；应在导入相关配置模块前设置。

按原消息标识去重，避免重连或重复事件创建多份下载任务。

把任务归属、下载状态和回传状态持久化，重启后才能继续查询和恢复。异常退出后的任务应先核对状态，再决定恢复或提示重试。

日志至少能关联任务编号、平台和错误类别，但不要保存或输出敏感凭据。清理文件时，只处理 Bot 管理目录内已过期且未被任务使用的文件。

当前验证主要在 Windows 环境完成。若部署到 Linux 或 Docker，需要单独验收浏览器、进程取消、文件锁、路径和媒体转换，不能直接把 Windows 验收结果视为服务器部署验收结果。

十、建议的首版范围

首版面向自己或熟人小群，采用用户和群白名单，只开放：

1. 单链接下载。
2. 任务进度查询。
3. 取消自己的任务。
4. 下载结果回传。
5. 必要的失败重试。

优先补齐结构化结果、任务归属、入口限额、消息去重和发送重试，再逐步开放作者批量下载与收藏功能。

建议增加的接入验收场景：

1. 同一消息重复到达，只生成一个任务。
2. 用户不能读取、取消或领取他人的任务。
3. 队列已满时能明确拒绝新任务。
4. 下载成功但发送失败时，只重试发送。
5. Bot 重启后能查到任务归属和回传状态。
6. Cookie 过期、平台限流和人机验证能返回明确状态。
7. 大文件、磁盘不足和任务超时能正确结束并清理资源。
8. Bot 与协议端分开部署时，结果文件仍能正确传递。
