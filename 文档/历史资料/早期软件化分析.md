# 爬虫软件化分析

## 当前目录整理

- `推特爬虫/`：已整理好的 X/Twitter 爬虫相关内容，包含源码、配置、Cookie、下载记录、ChromeDriver、旧版本和已下载媒体目录。
- `谷歌图片搜索工具/`：你自己做的 Google 相似图片搜索工具，当前先保留为独立模块。
- `build/`、`dist/`：看起来是 Google 图片搜索工具的打包产物，不并入 `推特爬虫/`。
- `原始需求.txt`：整体软件构思和后续任务说明，保留在当前历史资料目录。

运行推特爬虫时建议先进目录：

```powershell
cd .\推特爬虫
python .\twitter_Crawler_2.py
```

原因：当前推特爬虫默认按当前运行目录读取 `config.json`、`X_cookie.json`、下载记录等文件。

## 各项目用途

### 1. 推特爬虫

入口：`推特爬虫/twitter_Crawler_2.py`

当前能力：

- 使用 `X_cookie.json` 注入登录 Cookie。
- 支持单用户、批量用户下载。
- 支持图片、视频、GIF、视频音频提取。
- 维护已下载记录和失败 URL。
- 使用 Selenium 打开 X/Twitter 页面，从页面和网络 JSON 中提取媒体。

软件化难点：

- 现在偏命令行交互，很多状态通过 `print` 输出。
- 需要把下载过程封装成可被 GUI 调用的服务函数。
- 需要增加进度回调、日志回调、取消任务、暂停/继续。
- 默认路径依赖当前运行目录，后续应改成配置中心统一管理。

优先级：最高。它是现有代码里最接近你目标软件核心流程的模块。

### 2. PixivUtil2

目录：`Pixiv爬虫/`

用途：Pixiv / FANBOX / Sketch 下载工具。支持按画师、作品、标签、收藏、排行榜、小说、FANBOX 等多种方式下载，也有本地数据库管理功能。

Docker 情况：

- `Dockerfile` 只做三件事：使用 Python 3.11、安装 `requirements.txt`、安装 `ffmpeg`。
- 这说明它不是必须依赖 Docker。Windows 本地版本可以通过 venv + pip + ffmpeg 转成无 Docker 运行。

无 Docker 运行准备：

- Python 3.8+。
- `pip install -r requirements.txt`。
- 安装或放置 `ffmpeg.exe`。
- 准备 `config.ini`，Pixiv 登录建议使用浏览器 Cookie 中的 `PHPSESSID`。
- 可选：如果启用 XMP 元数据，Windows 需要 VC++ Redistributable 和 `pyexiv2`。

软件化难点：

- 主入口 `PixivUtil2.py` 是交互式菜单，很多功能通过 `input()` 驱动。
- 直接嵌入 GUI 不如 JMComic 简单。
- 推荐先做成“后台子进程执行 + 捕获输出”的方式，后续再逐步抽 API。

优先级：中。功能强，但改造成 GUI 服务层成本较高。

### 3. JMComic-Crawler-Python

目录：`JMComic爬虫/`

用途：JMComic 下载 API 和命令行工具。

当前特点：

- 核心 API 已经封装好：`jmcomic.download_album()`、`jmcomic.download_photo()`。
- 支持配置文件 `option.yml`。
- 支持搜索、详情、分类、收藏、图片解码、多线程下载、插件。

软件化优势：

- 本身就是 Python 包，比 PixivUtil2 更容易接入 GUI。
- 可以直接从 GUI 后台线程调用 API。
- 配置可以通过 YAML 文件生成，比交互式菜单更适合软件配置页。

优先级：高。适合作为第二个接入模块。

### 4. demjson-master

目录：`D:\xuexi\python\demjson-master`

用途：老 JSON 编码、解析、校验库，不是爬虫。

建议：

- 不要作为核心功能模块接入。
- PixivUtil2 已依赖 `demjson3`，优先使用项目自己的依赖。
- 新代码优先用 Python 标准库 `json`，只有遇到非标准 JavaScript 风格 JSON 时再考虑 `demjson3`。

优先级：低。

### 5. 谷歌图片搜索工具

目录：`谷歌图片搜索工具/`

用途：Google 图片 / Google Lens 相似图片搜索工具。

当前能力：

- Tkinter GUI 和 CLI 双入口。
- Selenium + ChromeDriver 上传本地图片。
- 提取外部来源 URL。
- 支持单图、文件夹批量、递归层数、代理、headless、CSV/TXT 输出。

软件化建议：

- 可以接入为“相似图片搜索/线索查找”模块。
- 它当前只提取 URL，不负责下载图片本体。
- 后续可以把提取到的 URL 投递给统一任务队列，再由对应下载器处理。

优先级：中高。适合做成统一软件里的辅助搜索入口。

## 推荐软件方案

推荐技术栈：Python + PySide6/Qt。

原因：

- 当前几个爬虫项目基本都是 Python，直接复用成本最低。
- PySide6 的桌面界面比 Tkinter 更适合做复杂管理软件。
- 支持表格、树形目录、任务列表、进度条、设置页、日志面板、系统托盘。
- 可以用后台线程或进程跑爬虫，GUI 只负责展示状态。
- 后续如果要预览网页，可以考虑 Qt WebEngine；如果只预览本地文件，Qt 自带组件已经够用。

不优先推荐：

- C#：WPF/WinUI 做桌面确实成熟，但你现在的环境在 IntelliJ IDEA，不适合直接开发 C#，而且要额外封装 Python 爬虫。
- JavaFX：能做，但美观和现代桌面体验需要投入更多 UI 工作，和 Python 爬虫集成也绕。
- Tkinter：适合快速小工具，不适合你描述的多站点、任务队列、预览、下载库管理软件。
- Electron/Tauri：界面好做，但会引入前端工程和 Python 后端通信，第一版复杂度偏高。

## 推荐界面结构

主界面建议做成“内容下载管理器”，不要做成单一脚本窗口。

核心区域：

- 左侧：站点模块列表，例如 X/Twitter、Pixiv、JMComic、Google 相似图片、Bluesky、Instagram。
- 顶部：目标输入区，支持用户名、URL、ID、关键词、图片路径。
- 中间：搜索结果 / 目标确认区，显示头像、标题、作者、状态、预览缩略图。
- 右侧：下载设置，选择类型、保存目录、线程数、代理、Cookie/账号配置。
- 底部：任务队列，显示进度、速度、已下载数量、失败数量、日志。
- 下载库：查看已下载内容，按站点、作者、标签、日期筛选。

第一版 MVP：

1. 只接入 X/Twitter。
2. 做目标输入和目标状态确认。
3. 做下载类型选择。
4. 做任务进度、日志、失败列表。
5. 做已下载文件列表和本地预览。

第二版：

1. 接入 JMComic。
2. 增加统一配置中心。
3. 增加下载库 SQLite 数据库。
4. 增加任务暂停、取消、重试。

第三版：

1. 接入 PixivUtil2 无 Docker 版本。
2. 接入 Google 相似图片搜索。
3. 支持在线网页预览和从预览页一键添加下载任务。

后续扩展：

1. 接入 Bluesky 图片/视频下载。
2. 接入 Instagram 图片/视频/Reels 下载。
3. 两者都先按“单目标下载 + 登录态配置 + 限流提示”做，不一开始做大规模批量抓取。

## 下一步开发建议

先做 PySide6 原型，并且先重构推特爬虫：

1. 把 `twitter_Crawler_2.py` 中的命令行输入、配置读取、下载执行拆开。
2. 新建一个 `twitter_service.py`，提供 `prepare_target()`、`download_target()`、`set_cookie()` 这类 GUI 可调用函数。
3. 给下载流程加 `on_log`、`on_progress`、`on_result`、`on_error` 回调。
4. GUI 用后台线程调用服务函数，主线程只更新界面。
5. 下载记录统一写入 SQLite，同时保留现有 JSON 记录兼容。

这样做的好处是：先把已有推特爬虫变成一个稳定模块，再逐步把 JMComic、Pixiv、Google 工具作为插件式模块接入。

## 15. `原始需求.txt` 更新后的需求基线

`原始需求.txt` 后续增加的内容已经超出“把几个爬虫接进 GUI”的范围，当前产品应按统一内容下载器设计。完整拆分见：

```text
../功能路线图.md
```

本节覆盖前文中较早的优先级建议：

- 核心对象从单个平台下载扩展为“目标、网址、搜索结果、任务、资源、历史记录”。
- X/Twitter 仍是第一优先级，但需要补齐关注列表导入/导出、用户搜索、预选列表、推文 URL、成功/失败清理和主页外链。
- JMComic 需要支持最多 15 个候选入队、同时最多 3 个漫画下载、搜索/预览/标签和限流停止。
- Pixiv 需要增加收藏夹搜索、日期筛选、作品类型和 AI 过滤。
- E-Hentai/ExHentai 被纳入后续平台，但必须单独处理代理提示、收藏夹、日期筛选、压缩包/种子下载和 `.eh`/种子保留。
- 压缩、解压缩、格式转换、PDF、长图、CSV、邮件发送和资源清理属于跨平台公共服务，不应分别复制到每个适配器。
- 下载目录、历史记录、文件命名和 URL 批处理必须在核心层统一。

本文是早期分析，当前实现状态请以 `../开发与架构说明.md` 为准。
